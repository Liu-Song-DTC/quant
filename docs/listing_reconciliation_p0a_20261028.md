# P0-a 交付: 上市名册对账 — 在册代码缺数据不得静默缩小股票池 (2026-10-28)

按交接计划 §5 的 P0 首项交付，格式遵循 §1.6。

## 问题与成因

1. **下载失败不阻断**：`data/akshare_kline_downloader.py:run()` 把每只股票的异常转成
   `FAIL:…` 状态，重试后仍失败也只写状态日志，**函数正常结束** ⇒ 刷新链继续往下走。
2. **新鲜度门禁只枚举现存文件**：`strategy/check_data_freshness.py:check_kline()` 遍历
   `BT_DIR` 里**已存在**的 `*_qfq.csv` ⇒ 缺失的股票根本不在视野里。
   计划中的隔离样例已复现：只放一份 `sh000001_qfq.csv` 时，
   `check_kline(2026-10-28)` 返回 `(True, 'K线: 1只全部新鲜…')`。
3. **换名前无集合对账**：`data/refresh_all.sh` 的 3b 步守卫是**内容级**（负价/倒挂/丢行），
   不检查"应有上市代码是否都有文件" ⇒ 少一只在册股票不会阻断换名。

### 真正的机制（新发现，比原描述更深一层）

`data/rebuild_table_qfq.py` 的重建主循环原本要求 **生产里已有 qfq 文件**才重建：

```python
if not (os.path.exists(bp) and os.path.exists(rp)):
    stats['missing'] = stats.get('missing', 0) + 1
    continue
```

⇒ **新上市股票永远没有生产文件 ⇒ 永远不被重建 ⇒ 永远进不了价格库 ⇒ 永远不进股票池**，
且只以 `stats['missing']` 计数留痕。实测 10-26 刷新日志：
`表驱动重建 5365   指数 3   沿用生产 12   异常 {'missing': 1}`
—— 那 1 只就是 **301718（C通则，2026-10-22 上市，仅 2 根 bar）**。
⇒ 该缺口**会随时间累积**（每只新上市都永久缺席），是系统性的、不可见的股票池收缩。

## 剩余风险

1. **允许清单会随新上市增长**：每只新上市需人工登记一次，否则闸会拦。
   根治方式是启用 `--include-new`（需裁定），届时清单只保留真正的例外。
2. 名册对账**不校验数据内容**（负价/倒挂/丢行由 3b 守卫负责），两者互补不重叠。
3. 上游名册本身的口径（efinance 实时行情，剔退市行）决定了"在册"的定义；
   若上游把仍在交易的股票误判为退市行，会造成**假缺股** ⇒ 名册异常判定（数量骤降）
   只能挡住大规模误判，单只误判需要名册快照的人工抽查。
4. `--include-new` 未跑臂前不得进生产（§1.4：不能对已看过的年份反向调参）。
