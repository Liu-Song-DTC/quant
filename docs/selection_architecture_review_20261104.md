# 选股架构审查与改进顺序（2026-11-04）

## 当前链路

`data/refresh_all.sh` 更新数据，信号引擎和 ML 生成按日期的股票信号；
`PortfolioConstructor.build()` 在回测与实盘复用，决定候选股票和目标市值；
回测由 `bt_execution.py` 撮合，实盘由 `generate_trade_orders.py` 出单。
这个分层保留了组合决策的共用入口，但成交、账户状态、数据时点和审计尚未形成
单一契约，不能只凭组合类相同就宣称两条链路等价。

## 已核实的问题与处理

1. 原价实验臂曾对全部股票按 100 股买入。科创板 688/689 股票的规则是
   200 股起买，其后可按 1 股递增。现已把数量规则抽到
   `strategy/core/trading_lots.py`，供实盘出单、原价回测和审计复用。
   冻结原价臂的旧成交中有 9 笔科创板买入仅 100 股，旧结果因此包含不可执行成交。
2. 原价审计此前仍用“买入数量必须是 100 的倍数”，会错拒合法的科创板订单。
   已改成共用数量规则；全量原价臂须用封存数据与信号复跑后，才比较收益。
3. 回测和实盘分别实现目标总市值的 98% 缩放、现金与持仓的转换。
   当前两处逻辑看似相近，但现金红利待到账、挂单和不可卖持仓可能让可用资金
   口径不同。先用配对逐日决策审计找首个分歧，再决定是否抽成共享账户预算模块。

## 下一步的架构改进

1. **输入契约**：每次候选与组合决策明确 `as_of`、`known_at`、数据版本、
   价格口径和缺失状态。历史数据回修只通过快照进入研究，实盘只用当时已可见版本。
2. **候选漏斗可观测**：逐日记录股票池、可交易、信号、ML、风险闸、行业约束、
   现金约束各层的保留/淘汰原因和分数。用这些记录定位短期赢家在哪一步丢失，
   再提出因子或 ML 假设；避免用末端 NAV 猜测原因。
3. **单一组合与成交契约**：组合输出目标市值和决策原因；执行器用同一份市场
   规则校验价格、数量、费用和现金，返回成交与拒单原因。回测的账户状态和
   实盘台账按相同字段逐日对账。
4. **研究门禁**：固定数据、信号和成本，对策略改动做训练期/样本外和逐年
   配对比较，至少报告 1/3/5/10 日净胜率、NAV、Sharpe、最大回撤、换手、
   成交可行性及差异归因。收益改善必须经这些门禁验证，不能预先保证。
5. **性能**：保留内容寻址缓存和向量化矩阵，但拆开信号生成、组合决策和
   执行回放的缓存键。组合或成交实验应复用相同封存信号，不重新计算全市场 ML。

先完成科创板数量规则的全量配对实验，然后按数据时点、候选漏斗、组合/账户
一致性、因子与 ML、风险和性能的顺序推进。调仓频率留到短期胜率口径稳定后实验。
