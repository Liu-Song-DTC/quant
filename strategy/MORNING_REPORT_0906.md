## 二、锚点危机: 797,071不可复现 (夜间最大发现)

**现象**: 恢复run(19:42)得出797,071; 纯mp6探针(相同代码配置数据)得出953,695。

**排查链** (全部实证):
1. 因子parquet逐列比较: 19:42 vs 21:32两次构建 **0列差异** → 因子层相同
2. 同数据进程内双训练: val_ic逐位相同(0.09118048656013707) → ML训练无随机性
3. 21:32的chunk0 IC可精确复刻(0.0912 = 10交易日purge + regime0); 19:42的0.0921
   在regime 0/1/2全试下不可复现 → 19:42是E2D2残留代码态产物(与18:06实验run同IC序列)
4. **purge曾误诊(已修订)**: ML块的all_dates是密集交易日历(sh000001日历+早段补齐,
   prepare_factor_data原样返回), `_fp_days`=10 = 10交易日purge = 提交版 == 9/5全天
   行为(23/23 chunk样本数吻合, cum_err=0)。凌晨误加`//2`是真回归(run1 chunk0=
   209,512), 已回退。purge行本身无罪。
5. 19:42 run信号生成期间[AltData]三件套下载行穿插(19:5x-20:02) → 另类数据竞态,
   信号混合态
6. 旧代码指纹只覆盖9个core文件+yaml — bt_execution/signal_engine/ml_predictor/
   portfolio四个决定回测结果的文件**不在指纹内** → 执行层漂移对指纹不可见

**结论**: 797,071=E2D2残留态+另类数据竞态双重污染产物(无效锚); 830,353(E-D1)
=正确代码态; 953,695(mp6probe)=同代码态同数据的可复现新锚候选。夜间E-G1/H1/H4
全部基于同一purge行为的信号族 → 内部一致, 且三个否决对新锚953,695同样成立(见下文)。
